# Image storage and admin media management — Cloudflare R2

## Architecture

Uploaded images are stored as **private objects** in a Cloudflare R2 bucket. MySQL `media_files` holds a UUID, internal R2 object key, image MIME type, original filename, size and creation metadata. The R2 bucket does **not** need public access.

```text
Admin browser → POST /api/media (image bytes + ADMIN access JWT)
Express → verify role, MIME signature and ≤5 MiB → signed PUT → R2
        → insert metadata in MySQL → return /api/media/{id}/file
Public website → /api/media/{id}/file → Express signed GET → R2
```

The object key is generated by the server (`media/<UUID>.<ext>`), not derived from a user-provided path. Files are served with a verified image content type, `Content-Disposition: inline`, and `X-Content-Type-Options: nosniff`. The backend signs AWS Signature V4 requests using built-in Node.js cryptographic primitives; credentials never reach the browser.

### Media endpoints

| Method | Endpoint | Access | Purpose |
|---|---|---|---|
| GET | `/api/media?page=1` | ADMIN | List uploaded images (24/page) and storage configuration state |
| POST | `/api/media` | ADMIN | Raw binary JPEG/PNG/WebP with `Content-Type` and optional URL-encoded `X-File-Name`; max 5 MiB |
| GET | `/api/media/:id/file` | Public, rate-limited | Serve image from private R2 bucket |
| DELETE | `/api/media/:id` | ADMIN | Delete only if image is not referenced by offers or trends |
| GET | `/api/site-content/admin/trends` | ADMIN | List current Hot Trend entries |
| POST | `/api/site-content/admin/trends` | ADMIN | Add a trend using an uploaded media image |
| PUT | `/api/site-content/admin/trends/:id` | ADMIN | Update trend image/title/link/order |
| DELETE | `/api/site-content/admin/trends/:id` | ADMIN | Remove a trend record (does not delete media file) |

The original public `GET /api/site-content` and offers APIs remain backward-compatible. The existing images referenced from Google Drive and `/nails/...` continue to work until replaced by an admin. **This change does not automatically download/migrate Google Drive images**: R2 access must be configured and each legacy image can be replaced through Admin.

## Provision Cloudflare R2

1. Sign in to Cloudflare and open **R2 Object Storage**. Ensure billing/R2 access is activated as required for your account.
2. Create an R2 bucket, e.g. `serpente-media`. The bucket is private. **Do not enable public development URL or a public custom-domain URL.**
3. Navigate to R2 **API Tokens** and create a token with **Object Read & Write** permissions **restricted to the single media bucket**. Preserve the generated **Access Key ID** and **Secret Access Key**; secret is shown only once.
4. Find your Cloudflare **Account ID** (32 hex characters).
5. Set these four variables on the **Railway API service** (not Vercel and not GitHub):

   | Environment variable | Value |
   |---|---|
   | `R2_ACCOUNT_ID` | Cloudflare account ID |
   | `R2_ACCESS_KEY_ID` | R2 API key ID |
   | `R2_SECRET_ACCESS_KEY` | R2 secret key |
   | `R2_BUCKET` | Bucket name |

   The backend connects to `https://<account_id>.r2.cloudflarestorage.com/<bucket>/...` using the S3 API and `auto` region.

6. Apply the new `AddMediaFiles1791452400000` TypeORM migration **before starting the new backend** (production startup checks pending migrations). Backup MySQL before migration.
7. Release backend and frontend from the same merged source commit; verify Railway `SUCCESS` and Vercel `READY`.

**Do not paste R2 keys into pull requests, source, chat messages or frontend environment variables.** Use Railway's secure variables UI. Rotation requires updating `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` together.

## Admin workflow

1. Log into `/admin` with an ADMIN account.
2. Open **Thư viện ảnh** to upload, preview and remove unused images.
3. Open **Ưu đãi** → Add/Edit → choose or upload an image instead of pasting an external URL.
4. Open **Hot Trend** → choose or upload an image, enter the Instagram post URL, title/order, and save.
5. To delete an image currently used by an offer or trend: replace the referenced image first, then delete the old media file from the library.

Upload is intentionally disabled in Admin while the R2 config is missing. The application continues serving legacy photos during rollout.

## Operational considerations

- **Private bucket:** The R2 bucket is not public; Express proxies media through `GET /api/media/:id/file`. This avoids configuring Cloudflare public bucket access/CORS and keeps existing Next.js image URLs same-origin.
- **Performance:** Signed R2 reads go through Railway; Next.js Image Optimization and HTTP caching reduce repeat requests. Heavy-traffic deployments may prefer a public cached image domain with cache invalidation, after implementing proper access policy.
- **Consistency:** Object storage and MySQL are separate systems. Upload attempts R2 cleanup if metadata insert fails. Deletion checks current references and removes the R2 object before the metadata row. Out-of-band storage failures are reported through API errors.
- **Media validation:** JPEG, PNG, WebP by signature; **5 MiB** upload limit; no SVG or executable files. The importer trusts file signatures and does not currently transcode/compress or sanitize image metadata; storage limits and security policy should be reviewed before allowing untrusted users to upload.
- **Backup:** Back up both MySQL and the R2 bucket (e.g. a separately stored sync/export) to recover the image mappings and binary objects together.
- **Data migration:** Existing Google Drive/Next static assets are **not deleted** automatically. After verifying uploads and replacements, the site no longer needs those original assets for the updated records.
